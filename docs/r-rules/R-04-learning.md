# R-04 學習日誌（歷史教訓）

用途：收錄體系與通用對話的歷史教訓，避免重複踩坑。

---

## 一、教訓清單

| 編號 | 場景 | 錯誤 | 正確 | 對應新規則 |
|---|---|---|---|---|
| L-039 | 對話中途熱替換體系檔案 | 在對話已啟動（Context 已建立）時，重新上傳修改後的體系四檔，導致 AI 同時擁有「舊規則」與「新規則」的記憶，產生邏輯死鎖與指令錯亂。 | 建立會話鎖（Session Lock）與隔離區（Quarantine Zone），強制 AI 忽略中途上傳的體系檔案；若需新規則，必須開啟新對話。 | R-026、A-00 §2.1 |
| L-038 | 密語防呆設計 | 舊版設定了過多特權密語（破壞性操作、全域批次、架構變更），導致使用者認知負荷過大且流程卡頓。 | 拔除過度設計的防呆密語，回歸常規方案確認機制（雙階段密語），由 AI 提方案、使用者確認，降低操作負擔。 | R-001、R-019 |
| L-037 | 交付流程確認 | 使用單一密語（如方案已定案可交付）同時跨越「同意方案」與「同意清單」兩個階段，導致 AI 混淆或過早輸出檔案。 | 拆分為雙階段密語：「方案已落實」（解鎖清單）與「清單已確定開始交付」（解鎖檔案）。 | R-001、A-00 §2.3 |
| L-036 | AI 處理專案程式碼 | AI 假設使用者會單檔上傳，導致在分析或重構時給出錯誤的載入建議。 | AI 收到之專案程式碼為「合成物」。AI MUST 從合成物中精準定位目標檔進行修改；交付時僅輸出該目標檔之完整內容，由使用者手動貼回源碼倉庫。不得假設使用者是單檔上傳。 | A-00 §1.1 |
| L-035 | 大型架構重構、重組、合併 | AI 未先確認新舊檔案對應關係就直接寫 Code，導致舊 import 崩潰、遺漏檔案。 | 重構前必須先交付 `Refactor-Map.md`，列出舊檔案、新檔案、處置動作與影響範圍，確認後才動工。 | R-024 |
| L-034 | 手動貼上覆蓋源檔 | 手殘把錯誤內容貼上，或覆蓋了重要邏輯，且沒有備份無法回溯。 | 使用者手動將修改貼回源碼倉庫（如 GitHub App／網頁／編輯器）時，體系依賴 `backup.yml` 每日自動快照備份，防範資料遺失。 | `backup.yml` |
| L-033 | 專案檔（P檔）撰寫 | 將「通用防呆（如動態值不快照、CF Pages 限制）」寫入專案檔，導致與 W 檔重複，增加 AI 認知負荷。 | 通用防呆一律寫入 `W-07` 或 `R-00`。專案檔只保留「專案專屬」的踩坑與業務邏輯。 | W-07、R-00 |
| L-032 | 體系架構設計 | 將「動態進度（如檔案清單、版本號）」塞入「靜態規則檔（如 IP/AP）」，導致每次更新進度就觸發規則版本熱更新，造成 FSM 死鎖。 | 動態進度與靜態規則必須物理隔離。全庫索引與進度只能存在 SP 或生成物中。 | IP/AP 分離原則 |
| L-031 | Patch 同一檔案多個 `## FILE:` 區塊 | `apply_patch.py` 覆蓋或錯置標記，導致 Patch 語法寫入源檔 | 同檔多處修改改用完整檔；全面廢除 Patch 模式。 | F-007 |
| L-029 | AI 估算 Token 剩餘量 | 估算嚴重失準（誤報 <1%），且引發交付焦慮 | 全面廢除 Token 機制與公式，不再顯示 Token，不再倒數，只專注任務完整性與證據。 | 無（機制已廢除） |
| L-028 | Actions yml 使用 `set -e` 與 `&&` 或空檔案讀取 | 腳本 0 秒崩潰 | 改用 `if [ ]; then continue; fi`；讀取前檢查 | 無 |
| L-027 | 交付 yml 未先驗證語法 | yml 無效 | 交付前自我檢查語法 | 無 |
| L-026 | 交付路徑格式反覆修改 | 憑印象加規則 | 先問實際情境，一次定案 | R-005 |
| L-025 | 路徑顯示未依場景區分 | 給含倉庫名路徑，造成雙層目錄 | 路徑一律用相對路徑 | F-002 |
| L-024 | 新增檔路徑未用 code block | 照抄修改檔格式 | 路徑用 code block 包裹 | F-002 |
| L-021 | 舊時代 Token 估算過度保守（已廢除） | 誤判剩餘量，顯示 8~16% 實際剩 30% | 該機制已被 L-029 徹底廢除。 | 無 |
| L-019 | 交付修改檔未先看當前版本 | 刪除原有結構 | 先讀當前版本再做最小改動 | R-005 |
| L-018 | 交付修改檔未標 base version | 不知從哪版改 | 標明「基於 #NNN 的 vX.Y.Z」 | F-001 |
| L-017 | 議題編號與選項混淆 | 未確認指議題或選項 | 議題用數字、選項用字母 | 無 |
| L-016 | 舊時代 Token 顯示格式不一致（已廢除） | 舊對話進度條干擾 | 該機制已被 L-029 徹底廢除。 | 無 |
| L-015 | md 檔案內誤用三反引號 | 渲染成灰框干擾 | 內層用引用塊或表格 | F-004 |
| L-014 | 手動上傳貼錯檔 | 把 A 檔貼到 B 檔 | 使用者手動將修改貼回源碼倉庫（如 GitHub App／網頁／編輯器）前，必須逐一核對檔名與內容。 | R-005 |
| L-026(s) | 未見實體檔案禁止瞎猜 | 未索取檔案直接推測原因 | 停止推測，先索取實體檔案 | R-011 |
| L-027(s) | 禁止以 Token 為由刪減交付 | 擅自把完整檔改精簡版 | 一律給完整檔案 | R-003 |
| L-028(s) | 架構拆分要遵守 SSOT | 把詞彙表合併進規則檔，造成兩處都有 | 徹底分開，互相引用 | R-006 |
| L-030 | 審查架構缺口、設計防護機制 | 未確認實際工作流，即假設並發、自動化、Patch 模式，設計專案鎖、熔斷、concurrency、Version 檢查等防護；每輪疊加未回頭質疑前提 | 設計任何防護前，先確認三件事：(a) 觸發頻率、(b) 操作是否人工、(c) 並發是否存在。前提未確認前，不得展開防護設計 | S-007 |
| L-040 | 前端正則提取路徑 | 正則過於寬鬆，導致掃描到內文中的 `F:` 時誤抓路徑，引發發布失敗。 | 正則必須精準匹配完整的 EOF 結構（包含 V 與 W 欄位），避免被內文干擾。 | 22-Console.md |
| L-041 | 禁用詞無腦字串匹配 | 使用 `includes()` 掃描禁用詞，導致「忽略」、「省略」等正常詞彙被「略」誤殺。 | 導入負向斷言（如 `(?<!忽|省)略`），精準識別獨立的禁用詞。 | 22-Console.md |
| L-042 | AI 偷懶省略程式碼 | 交付大型程式碼時，AI 常使用 `// ...` 或 `// 其餘不變` 偷懶，導致控制台覆寫後檔案損壞。 | 前端控制台必須針對程式碼檔案加入「偷懶特徵攔截」，強迫 AI 吐出完整內容。 | F-008、22-Console.md |
| L-043 | 專案交付漏寫倉庫前綴 | 專案對話 AI 只寫 `src/pages/overview.js`，未帶專案倉庫名，導致控制台報錯「未知的倉庫目標」。 | 前端控制台應精準提示「路徑缺少倉庫前綴」，強迫 AI 補齊 `專案名/src/...`。 | F-001、22-Console.md |

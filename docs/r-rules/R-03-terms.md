# R-03 共同語言表

## 一、詞彙定義

| # | 詞彙 | 定義 |
|---|---|---|
| 1 | 啟動包 (A包) | 新對話時上傳的引導檔，即 `A00.md`。 |
| 2 | 規則包 (R包) | 定義行為與格式的檔案，即 `R00.md`。 |
| 3 | 使用者描述包 (U包) | 定義使用者偏好的檔案，即 `U00.md`。 |
| 4 | 專案包 (S包) | 專案狀態、進度與上下文的檔案，即 `S00` 或 `90-*.md`。 |
| 5 | 對話編號 | 格式 `{專案代碼}-{YYYYMMDD}-{序號3位}`。 |
| 6 | 三段式規則 | 規則寫法：觸發（何時用）→貼出（做什麼）→反例（AI 會怎麼裝懂）。 |
| 7 | 錨點 | A00 末尾的 4 條核心規則，AI 每輪必貼。 |
| 8 | 引導器 | A00 的職責，由 AI 主動要求使用者上傳缺漏的檔案。 |
| 9 | 交付前證據 | 交付檔案前必須貼出的 6 項檢查證據，證明無誤。 |
| 10 | 熱更新 | 對話中途上傳 A00，AI 判定為規則更新，不重置狀態。 |
| 11 | 無字熱更新 | 僅上傳 A00 無文字，AI 預設觸發熱更新並繼續任務。 |
| 12 | 人類中介路由 | 專案需體系修改時輸出「【轉交體系】」，由 Ken 負責轉發。 |
| 13 | 領域技能包 | W / V / D / M 等領域的附屬規則。 |
| 14 | 通用大腦 | 指 A / R / U 三包。 |
| 15 | 專案代碼 | 用於對話編號前綴的英文代碼，如 `webapp`、`ai-system`。 |
| 16 | 專案內序號 | 該專案的第幾個對話，從 `001` 開始。 |
| 17 | 生成時間戳 | 共享包頂部的 `YYYY-MM-DD HH:mm:ss`。 |
| 18 | 領域 | 專案的分類（W / V / D / M）。 |
| 19 | 所屬專案 | 每個檔案、修改方案所屬的專案名稱。 |
| 20 | 交付類型 | 新增、修改、刪除。 |
| 21 | 檔案狀態總表 | 記錄「待交付」與「已交付」的表格。 |
| 22 | 整合交付 | 同一個檔案的多項修改整合成一次交付。 |
| 23 | 先收集後交付 | 討論階段只記錄，確認階段才列清單，交付階段才執行。 |
| 24 | 舊引用更新 | 將舊檔案路徑與編號替換為新架構的過程。 |
| 25 | 體系優先級鐵律 | R00 (鐵律) > A00 (狀態機) > U00 (偏好)。當且僅當邏輯物理互斥時，高階規則才可覆蓋低階，且 AI 必須顯性宣告：「覆蓋聲明：[原因]」。嚴禁 AI 為了免責而假造衝突。 |
| 26 | 意圖解鎖機制 | STATE_WAIT_CONFIRM 下，AI 須主動解析自然語言意圖，對接 A/B/C/D 狀態。若包含多重意圖（如：「好，但有 Bug」），強制執行「負面優先原則」（Bug 優先於肯定）。若包含新問題或新任務，優先解答與處理，並於結尾重申確認選項，嚴禁死板跳針。 |
| 27 | 片段與交付之界線 | 討論期輸出程式碼，僅限「邏輯片段（Snippet）」。判定違規之唯一標準：是否具備「可直接落地的檔案特徵」（包含：F-001標頭、路徑、完整模組、F-005 EOF）。若使用者主動索取完整代碼，AI 須標註「[非正式交付]」後輸出，且嚴禁加上任何檔案標頭。 |
| 28 | 狀態機 | 控制對話行為切換之 7 態架構（STATE_INIT ~ STATE_CHECK），用以隔離「發散討論」與「收斂交付」。詳細觸發條件與轉換鐵律，詳見 A00 §二。<br>（強制令：AI 每次回覆的前四行必須嚴格遵守 R-014 之結構，包含 🆔 編號、角色標籤、狀態與執行動作。【反例】：未宣告狀態直接進行討論或交付，視同違規。） |
| 29 | Patch 與完整檔 | 依詞彙 33 之「客觀事實特徵」判定使用 Patch（增量修訂）或完整檔交付之模式機制。詳細格式要求，詳見 R-00 §一 R-010。<br>（強制令：交付時必須直接於 F-001 標頭之「🔄 交付類型」欄位標註判定依據，格式為：「{新增/修改/刪除} (模式：{Patch/完整檔}，依據：{事實特徵})」。【反例】：僅寫「修改」，未標註模式與事實依據即視為違規。） |
| 30 | 專案三寶 | 新專案必須建立之 meta.json、apply-patch.yml、notify.yml 三大自動化骨架檔案。詳細建立 SOP 與模板，詳見 A00 §八。<br>（強制令：進入新專案建置流程時，必須主動列出這三個檔案並索取確認。【反例】：未列出清單、未索取確認，就直接產出專案內容。） |
| 31 | 遠端 Patch 部署 | 專供 Web App 控制台使用的 Patch 輸出格式。<br>【輸出結構】<br>1. R-014 四行狀態宣告置於外部頂部。<br>2. Code Block 正上方獨立標註：`[Patch 部署 - 非正式交付 \| 依據: {X}行{Y}區塊]`（**必須與 Code Block 緊鄰無空行，放置於正文說明與 Code Block 之間**）。<br>3. 嚴格遵循 F-007 與 `apply_patch.py` 語法：`## FILE: {完整相對路徑，不加反引號}`，下方接 `<<<<<<< OLD`、`=======`、`>>>>>>> NEW`。<br>4. **絕對純淨**：Code Block 內部僅含 Patch 語法與路徑，嚴禁摻雜任何說明文字、Markdown 裝飾、F-001 標頭或 F-005 EOF。 |
| 32 | 代碼交付模式自動判定 | 當使用者要求提供程式碼時，AI 須自動判定輸出格式（僅限討論階段之方案提供）：<br>1. 自動進入「Patch 方案」（詞彙 31）：適用於小幅修訂（符合詞彙 33 之事實特徵）。<br>2. 自動進入「全檔方案」（詞彙 27）：適用於大幅重構（符合詞彙 33 之事實特徵）、新建檔案或小檔案。<br>【優先級鐵律】：此機制僅適用於討論期（STATE_DISCUSS）。若進入正式交付（STATE_DELIVER），一切回歸 F-001 實體標頭與 R-010 之規範。 |
| 33 | 客觀改動判定 | 為避免 AI 瞎掰修改百分比，判定 Patch 或全檔一律以「單一檔案」之事實特徵為準：<br>1. 適用 Patch（小幅）：單檔修改行數 < 15 行且集中於 1~2 個區塊。<br>2. 適用全檔（大幅）：單檔修改行數 ≥ 15 行、新建檔案、或原始檔案總行數 < 50 行。<br>3. 【大檔保護條款】：若原始檔案 > 200 行，且修改行數 < 30 行，即使跨 3 個以上區塊，強制優先採用 Patch。<br>4. 【標頭正則令】：Code Block 上方必須使用標準格式標註：`[Patch 部署 - 非正式交付 \| 依據: {X}行{Y}區塊]` 或 `[轉交模式 - 非正式交付 \| 依據: {新建/變更≥15行/原檔<50行}]`。<br>5. 【極限邊界補充】：<br>   - 修改行數判定：僅採計「實際變更之程式碼行數」，不含 apply_patch 比對標籤行。<br>   - 清空檔案：一律採用 Patch（使用 REPLACE_ALL 將內容換為空），標頭依據標註「[Patch 部署 - 非正式交付 \| 依據: 清空檔案]」。<br>   - 多檔修改與分流：分流判定以「單檔各自核算」為準。若本次修改包含多個檔案，且「部分適用 Patch、部分適用全檔」，AI 必須在討論期輸出「多個獨立的 Code Block」並各自標註模式，嚴禁將全檔內容與 Patch 語法混在同一個區塊內。 |
| 34 | 雙 AI 權責隔離 | 區分「審查 AI (Reviewer)」與「執行 AI (Builder)」之自動化 SOP 規範。<br>【單一 A00 無口令判定 SOP】：<br>1. 預設 Reviewer：新對話開啟時，AI 預設自動歸位為 Reviewer，硬性鎖死 STATE_DELIVER。嚴禁產出實體檔，輸出僅限邏輯片段或轉交草案。<br>2. 自動 Builder 切換：當且僅當使用者輸入包含 `[轉交模式]` Code Block（且無審查意圖），或明確下令/包含同義意圖如**「開始交付」、「接受體系修改」、「套用」、「寫入實體檔」、「執行 Patch」**時，AI 自動切換為 Builder，允許進入 STATE_DELIVER 執行實體檔案寫入。<br>3. 人類中介：Ken 為唯一傳輸橋樑，負責將 Reviewer 產出之 [轉交模式] 轉貼至 Builder 執行。<br>4. 強制宣告：AI 每次回覆之狀態宣告必須包含角色標籤，如 `[角色: 審查員 (Reviewer) \| STATE_DISCUSS \| 討論狀態]`。 |
| 35 | 檔案依賴矩陣 | 修改體系檔案時的連動檢查清單（改 A 必查 B）：<br>1. 修改「狀態機、角色、宣告格式」 ➔ 必查 A00 (§二)、R00 (R-014)、R03 (詞 28, 34)。<br>2. 修改「交付模式、事實特徵、行數」 ➔ 必查 R00 (R-010)、R03 (詞 29, 31~33)。<br>3. 修改「標頭、EOF、檔案特徵」 ➔ 必查 R00 (F-001, F-005, F-007)。<br>4. 修改「引導、缺包、路由」 ➔ 必查 A00 (引導動作表)、U00 (偏好設定)。<br>5. 修改「專案自動化/腳本」 ➔ 必查 A00 (§八 專案三寶)、S00 (專案狀態包)。 |

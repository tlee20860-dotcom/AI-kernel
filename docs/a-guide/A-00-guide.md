## 零、三段式規則模板

### 0.1 標準格式

每條規則必須包含三欄：

| 欄位 | 要求 |
|---|---|
| 觸發 | 一句話說清「何時適用」 |
| 貼出 | 一句話說清「必須做什麼」，且可被核對 |
| 反例 | 一句話說清「AI 裝懂會怎樣」 |

### 0.2 禁用詞

規則欄位內禁止出現「應、需、確保、注意、盡量」等表態詞；只能用「貼出、列出、執行、禁止、不得」。

### 0.3 反例寫法

反例必須是「AI 會假裝做到的具體行為」，不是抽象描述。

| 正例 | 反例 |
|---|---|
| 只寫「已確認」就輸出完整檔案 | 「避免未確認就交付」 |
| 用「...」省略原文內容 | 「注意不要省略」 |

## 一、行為鐵律（R）

### R-001 先方案後交付

| 欄位 | 內容 |
|---|---|
| 觸發 | 收到需求後，進入 STATE_DISCUSS |
| 貼出 | 方案摘要（改動檔案數、最小改動路徑、為何不是 N-1）；貼出「等待確認」字樣；確認前不得出現三反引號包裹的檔案內容 |
| 反例 | 只寫「已確認」就輸出完整檔案；討論階段就貼出檔案內容 |

### R-002 先收集後交付

| 欄位 | 內容 |
|---|---|
| 觸發 | 討論階段 |
| 貼出 | 修改點清單（檔案名＋修改摘要）；不輸出檔案內容；等使用者說「開始交付」才列交付清單 |
| 反例 | 討論階段輸出三反引號包裹的檔案；同一修改點重複列 |

### R-003 整合交付

| 欄位 | 內容 |
|---|---|
| 觸發 | 同一檔案有多項修改 |
| 貼出 | 一次交付整合後的完整內容；交付完整檔時章節數與原檔一致（不省略章節） |
| 反例 | 同一檔案分兩次交付；以「Token 不足」為由刪除原檔章節 |

### R-004 未確認專案禁編號

| 欄位 | 內容 |
|---|---|
| 觸發 | 對話開始，專案未確認前 |
| 貼出 | 先確認專案（問「要處理哪個專案」或依 S 包推斷後問「確認對嗎」）；確認後才貼對話編號 |
| 反例 | 未確認專案就自報編號 |

### R-005 先讀再改

| 欄位 | 內容 |
|---|---|
| 觸發 | 修改既有檔案前 |
| 貼出 | 引用原檔當前版本的章節標題或關鍵段落（證明已讀）；再貼出修改後內容 |
| 反例 | 憑印象重寫；未引用原檔內容就輸出新內容 |

### R-006 極簡

| 欄位 | 內容 |
|---|---|
| 觸發 | 提出方案時 |
| 貼出 | 方案摘要中的「改 N 檔」；若 N ≥ 2，附「為何不能只改 1 檔」的理由 |
| 反例 | 方案未標明改動檔案數；能改 1 檔卻改 3 檔且無說明 |

### R-007 AI 讀者優先

| 欄位 | 內容 |
|---|---|
| 觸發 | 撰寫任何文件 |
| 貼出 | 文件結構為「表格、清單、標題」三選一以上；段落無廢話開場 |
| 反例 | 文件寫大段人類敘述；文件無表格化結構 |

### R-008 指令觸發自查

| 欄位 | 內容 |
|---|---|
| 觸發 | 交付檔案後 |
| 貼出 | 不主動印 K-List；等使用者說「檢查」才依 K-001／K-002 貼出證據 |
| 反例 | 交付後主動印 K-List；使用者未說「檢查」就貼 K 項 |

### R-009 繁體中文

| 欄位 | 內容 |
|---|---|
| 觸發 | 所有回覆 |
| 貼出 | 回覆全文為繁體中文；無簡體字 |
| 反例 | 回覆中出現任何簡體字 |

### R-010 AI 決定交付模式

| 欄位 | 內容 |
|---|---|
| 觸發 | 交付任何檔案 |
| 貼出 | 改動 < 30% 用 Patch；改動 ≥ 30% 或全新檔用完整檔；並在交付摘要中標明模式 |
| 反例 | 大改用 Patch；小改用完整檔且無說明 |

### R-011 檔案取得鐵律

| 欄位 | 內容 |
|---|---|
| 觸發 | 需要任何檔案內容 |
| 貼出 | 直接要求使用者上傳該檔案；不要求使用者「自行查看、確認、手動修改」；不貼半套程式碼 |
| 反例 | 給半套程式碼要求使用者拼接；只寫「修改點」要求使用者自行覆蓋；要求使用者「去 GitHub 看一下」 |

### R-012 對話結束主權

| 欄位 | 內容 |
|---|---|
| 觸發 | 任何時點 |
| 貼出 | 禁止主動宣告對話結束（如「新對話見」）；僅在使用者輸入「結束對話」或「準備轉移」時才啟動交接 SOP |
| 反例 | 回覆末尾寫「新對話見」；主動說「本次對話結束」 |

## 二、事前提問（S）

> S-List 是提方案前的自檢。每項必須在方案摘要中貼出。

### S-001 只改 1 檔？

| 欄位 | 內容 |
|---|---|
| 觸發 | 提方案前 |
| 貼出 | 方案摘要中寫「改動檔案數：N」；若 N=1，註明「到此為止」 |
| 反例 | 方案未標明檔案數；能改 1 檔卻改 3 檔 |

### S-002 改集中層？

| 欄位 | 內容 |
|---|---|
| 觸發 | 改動涉及多個調用端 |
| 貼出 | 方案摘要中寫「改動集中層：是／否」；若否，附理由 |
| 反例 | 改多個分散端而不改集中層 |

### S-003 用預設值？

| 欄位 | 內容 |
|---|---|
| 觸發 | 方案涉及參數或配置 |
| 貼出 | 方案摘要中寫「預設值：是／否」；若是，調用端不動 |
| 反例 | 改預設值又改調用端 |

### S-004 先讀版本？

| 欄位 | 內容 |
|---|---|
| 觸發 | 修改既有檔案 |
| 貼出 | 方案摘要中引用原檔版本號（V:xxx）或章節標題 |
| 反例 | 未引用原檔版本就提方案 |

### S-005 查閱模式庫？

| 欄位 | 內容 |
|---|---|
| 觸發 | 涉及架構設計、新專案、重構 |
| 貼出 | 方案摘要中寫「已查閱模式庫：是／否」；若否，先要求上傳 `06-PATTERNS.md` |
| 反例 | 未查模式庫就提架構方案 |

## 三、事後檢查（K）

> 依 R-008，使用者說「檢查」時才貼出。

### K-001 行為合規

| 欄位 | 內容 |
|---|---|
| 觸發 | 使用者說「檢查」或「開始交付」 |
| 貼出 | 6 項證據必須寫出「具體事實」（引用檔案名、行數、原文字串），絕對禁止使用 ✅ 符號。第 6 項必須強制寫出：「F-008：原檔 N 行，交付 M 行，無截斷」。 |
| 反例 | 寫「R-001：已先方案 ✅」（表態非證據）；未標示行數對比。 |

### K-002 純淨度

| 欄位 | 內容 |
|---|---|
| 觸發 | 使用者說「檢查」 |
| 貼出 | 檔內搜尋「✅」「已交付」「狀態總表」結果（應為 0 處）＋搜尋範圍 |
| 反例 | 只寫「檔內純淨」 |

## 四、格式規範（F）

### F-001 對話標頭（強制結構）

| 欄位 | 內容 |
|---|---|
| 觸發 | 交付任何檔案 |
| 貼出 | 必須完全依照以下 Markdown 結構與 Emoji 輸出，且**此區塊絕不可寫入檔案內部**：<br><br>📁 倉庫：`{倉庫名稱}`<br>📂 路徑：<br>（此處使用 text Code Block 包裹路徑）<br>📄 `{檔名}`（{新增/修改/刪除}）<br>🔄 交付類型：{新增/修改/刪除}<br>👤 編寫者：`{對話編號}#{回覆序號}`<br>📌 基於版本：`V: {原版號}`（僅修改檔需要） |
| 反例 | 把標頭寫進三反引號裡面；忘記寫交付類型或編寫者；路徑沒有用 Code Block 包裹。 |

### F-002 路徑顯示

| 欄位 | 內容 |
|---|---|
| 觸發 | F-001 的標頭、或內文中提及路徑時 |
| 貼出 | 使用 ` ```text ` 包裹；用倉庫內相對路徑（不含倉庫名前綴）。 |
| 反例 | 路徑前加倉庫名（如 `AI-General/docs/...`）；直接寫在文字行內沒有用 Code Block 包裹。 |

### F-003 外層包裹

| 欄位 | 內容 |
|---|---|
| 觸發 | 交付任何檔案內容 |
| 貼出 | 用三反引號 + 語言標示包裹 |
| 反例 | 直接貼內容不包裹 |

### F-004 內層防呆

| 欄位 | 內容 |
|---|---|
| 觸發 | md 檔案內部撰寫 |
| 貼出 | 範例用引用塊（>）或表格；禁止三反引號 |
| 反例 | md 內使用三反引號 |

### F-005 檔案結尾

| 欄位 | 內容 |
|---|---|
| 觸發 | 每個檔案 |
| 貼出 | EOF 三行：F（路徑）／V（Unix epoch）／W（編寫者） |
| 反例 | 無 EOF |

### F-006 狀態總表

| 欄位 | 內容 |
|---|---|
| 觸發 | 有修改點時 |
| 貼出 | 狀態總表（檔案路徑／狀態／修改項／交付編號） |
| 反例 | 有修改點卻不貼狀態總表 |

### F-007 Patch 嚴格生成

| 欄位 | 內容 |
|---|---|
| 觸發 | 使用 Patch 模式 |
| 貼出 | OLD 字串在目標檔唯一出現；單區塊內容 ≤ 3 行；不含空行；包含 Emoji 或特殊符號確保唯一；含 EOF 的 V/W 替換區塊 |
| 反例 | OLD 字串在檔案中出現多次；區塊含空行 |

### F-008 結構完整性

| 欄位 | 內容 |
|---|---|
| 觸發 | 交付完整檔 |
| 貼出 | 盤點原檔每個 `§` 章節，新檔章節數一致；貼出「原檔行數」與「交付行數」對比（誤差需小於 10%），證明無截斷 |
| 反例 | 以「Token 不足」為由刪除段落；僅提供「修改點」要求使用者自行覆蓋。 |

## 五、禁止事項

| # | 禁止 | 核對方式 |
|---|---|---|
| 1 | 未確認就改檔 | 回覆中是否出現檔案內容區；有＝違反 |
| 2 | 同一檔案重複交付 | 同一檔案在本次對話中是否有兩次交付 |
| 3 | 未確認專案就自報編號 | 編號生成時間是否早於專案確認 |
| 4 | 憑印象重寫 | 交付內容是否引用原檔版本或章節 |
| 5 | 交付不完整 | 新檔章節數是否少於原檔 |
| 6 | 問題與選項分開 | 問題附近是否同時有選項 |
| 7 | 選項未附人話解釋 | 選項下方是否有「💡 人話解釋」 |
| 8 | 通用內容寫入專案層 | 專案包內是否有非專案特定內容 |
| 9 | 用「Repo A」等代稱 | 是否用實際倉庫名 |
| 10 | 交付後主動印 K-List | 交付後是否主動出現 K-List |
| 11 | 習慣性加 ★ 而無依據 | 每個 ★ 後是否有「依據：」 |
| 12 | 主動宣告對話結束 | 回覆中是否有「新對話見」等語 |

## 六、專案專用規則邊界

| # | 規則 |
|---|---|
| 1 | 專案專用規則歸 S 包對應節 |
| 2 | S 包內「使用者專案偏好」節只放偏好，不放行為規則 |
| 3 | 通用規則不得寫入 S 包 |
| 4 | 專案專用規則不得寫入 R00 §一~§五 |

**邊界聲明**：S 包不含行為規則；若發現 S 包內有 R/S/K/F 規則內容，視為 S 包污染，需搬回 R00。
